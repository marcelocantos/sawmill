### F1 — [CRITICAL] Undo of a modified originally-empty file DELETES the file (data loss)

- **Location:** `go/forest/forest.go:268`
- **Dimension:** -
- **Invariant violated:** An empty backup blob must correspond ONLY to a file that did not previously exist; a file that existed (even with 0 bytes) must be restored to its prior content on undo, never deleted.
- **Failure scenario:** A tracked file exists on disk but is empty (e.g. an empty __init__.py, a placeholder config, or a package marker). A transform that adds content to it (codegen edit keyed to that path — see go/codegen/codegen.go:288-295 which emits a FileChange with Original=[]byte{}) is applied. In ApplyWithBackup step 2, os.Stat(change.Path) succeeds so copyFile runs and writes a 0-byte backup (forest.go:208-211). apply then writes the new content and the file now has data. On undo, backupContent has len 0 and the file still exists, so origExists is true: the `len(backupContent)==0 && !origExists` branch is skipped and control falls into `if len(backupContent)==0 { os.Remove(original) }`. The user's file is REMOVED entirely instead of being restored to empty. Verified: an existing empty file yields a 0-byte backup indistinguishable from the 'new file' marker (repro printed `empty file backup len=0`).
- **Evidence:**

```
if len(backupContent) == 0 && !origExists {
			_ = os.Remove(backup)
			continue
		}

		if len(backupContent) == 0 {
			// File was newly created — remove it.
			_ = os.Remove(original)
		}
```

- **Fix sketch:** Stop overloading empty content as the 'new file' sentinel. Record whether the original existed at backup time (e.g. write a sibling `.meta` marker, or use a distinct sentinel filename like `<path>.absent` for genuinely-new files, or store a manifest of {path, existed, mode} alongside the backups). In UndoFromBackups, delete-on-undo only when the manifest says the file did not previously exist; otherwise always os.WriteFile the (possibly empty) backup content back.
- **Verification:** Before: write a Go test that creates an empty file under a temp root, runs ApplyWithBackup with a FileChange{Original:[]byte{},NewSource:[]byte("x")}, then UndoFromBackups, and asserts os.Stat(path) succeeds with 0 bytes — it currently fails with ENOENT (file deleted). After the fix the same test passes.

### F2 — [CRITICAL] rename_file destination is not contained to the project root — `to` with `..` (or an absolute path) escapes the root and overwrites arbitrary files with no backup (permanent data loss)

- **Location:** `go/mcp/tools.go:1949`
- **Dimension:** -
- **Invariant violated:** rename_file's destination must stay inside the bound project root; transforms (and their apply step) must only create/overwrite files within the intended root, and every write must be recoverable via undo.
- **Failure scenario:** A session bound to root R calls rename_file(from="src/a.go", to="../../.zshrc") (or to="/absolute/victim"). handleRenameFile sets absTo=filepath.Join(root, to), which filepath.Cleans the `..` and yields a path OUTSIDE R (e.g. ~/.zshrc). `from` is validated against tracked files so it is in-root, but `to` is never checked. On apply(confirm=true), handleApply runs os.MkdirAll(filepath.Dir(r.To)) then os.Rename(r.From, r.To) (tools.go:1236-1239), moving a.go on top of the external file and clobbering it. Renames are NOT passed through ApplyWithBackup (only h.pending.Changes are), so no backup exists and undo cannot restore the destroyed file. Reproduced in scratchpad: an external VICTIM.txt containing "IMPORTANT ORIGINAL CONTENT" ended up containing "package a" after the escaped rename, with the original content permanently lost. (The same lack of an existence/backup check also silently destroys an in-root file when `to` names an existing tracked file.)
- **Evidence:**

```
absFrom := filepath.Join(root, from)
absTo := filepath.Join(root, to)
// ... no containment check on absTo ...
renames := []FileRename{{From: absFrom, To: absTo}}
// handleApply:
if err := os.MkdirAll(filepath.Dir(r.To), 0o755); err != nil { ... }
if err := os.Rename(r.From, r.To); err != nil { ... }
```

- **Fix sketch:** In handleRenameFile, after computing absFrom/absTo, reject any `to` that escapes the root: rel, err := filepath.Rel(root, absTo); if err != nil || rel == ".." || strings.HasPrefix(rel, ".."+string(os.PathSeparator)) { return error }. Also reject when absTo already exists (or route the rename through a backup so undo can revert it). Apply the same containment to absFrom for defense in depth. Consider a shared containsPath(root, p) helper (none exists in the repo today) used by every path-joining handler.
- **Verification:** Before: add a Go test in go/mcp that builds a Handler with a model rooted at t.TempDir(), writes an external sibling file, calls handleRenameFile(from=<valid tracked file>, to="../victim.txt"), then handleApply(confirm=true); assert the external file is clobbered (bug present) — or run the scratchpad repro at /private/tmp/.../audit-repro/sawmill/repro.go which prints the victim overwritten. After: the same handleRenameFile call returns an error, os.Stat on the external file shows original content intact, and no rename is staged.

### F3 — [HIGH] Apply and undo discard the original file's permission bits (0o644 hardcoded)

- **Location:** `go/forest/forest.go:196`
- **Dimension:** -
- **Invariant violated:** Rewriting a file must preserve its mode/attributes; an executable file must remain executable after a transform and after an undo.
- **Failure scenario:** An executable script tracked by an adapter — e.g. a Python entrypoint with a shebang and mode 0o755 — is transformed (rename, promote_constant, codegen, etc.). ApplyWithBackup writes the staging temp with 0o644 (line 196) then os.Rename replaces the original inode, so the file's mode becomes 0o644 and it is no longer executable (verified: rename of a 0o644 temp over a 0o755 file yields 0o644). Undo does not recover it either: UndoFromBackups line 272 uses os.WriteFile(original, ..., 0o644), which for an existing file leaves the current (already-broken 0o644) mode untouched (verified: WriteFile perm arg is ignored on an existing file). The execute bit is permanently lost across apply and undo, breaking the script.
- **Evidence:**

```
if err := os.WriteFile(temp, change.NewSource, 0o644); err != nil {
			return nil, fmt.Errorf("writing temp %s: %w", temp, err)
		}
		tempPaths = append(tempPaths, temp)
```

- **Fix sketch:** Stat the original before writing and carry its os.FileMode through: write the staging temp with the original mode (or os.Chmod after rename), and in UndoFromBackups os.Chmod the restored file to the mode captured in the backup manifest. copyFile already preserves mode into the backup (line 300) but that mode is never re-applied to the live file.
- **Verification:** Before: create a 0o755 file, run a transform+apply, os.Stat → 0o644; undo, os.Stat → still 0o644. After the fix both operations preserve 0o755.

### F4 — [HIGH] apply() never re-checks pending.Original against current disk — concurrent applies on a shared model silently clobber committed changes

- **Location:** `go/forest/forest.go:208`
- **Dimension:** -
- **Invariant violated:** Pending changes assume the on-disk file still matches FileChange.Original at apply time; ApplyWithBackup must verify current content matches the previewed Original (optimistic-concurrency guard) before overwriting.
- **Failure scenario:** Sessions A and B share one CodebaseModel for root R via modelpool. A previews a transform of file X (h.pending.Changes[0].Original = v0). B previews and applies a different transform of X: disk X becomes v1 and the manager reparses. A then calls apply(confirm=true): handleApply (tools.go:1227) calls ApplyWithBackup, which at forest.go:208 stats X, backs up the *current* disk content v1, then at forest.go:228 renames A's staged NewSource (computed from v0) over X. B's committed change is silently overwritten and A is told 'Applied N change(s)'. There is no hash comparison anywhere between change.Original and the live file, so the lost update is undetectable. The same clobber happens single-session if the file changed on disk (watcher/external edit) between preview and apply.
- **Evidence:**

```
if _, err := os.Stat(change.Path); err == nil {
    if err := copyFile(change.Path, backup); err != nil { ... }   // backs up CURRENT disk, no compare to change.Original
} else { ... }
...
if err := os.Rename(tempPaths[i], change.Path); err != nil { ... }   // overwrites regardless of concurrent edits
```

- **Fix sketch:** Record a content hash of change.Original when the pending change is built, and in ApplyWithBackup re-read each change.Path and compare its hash before the step-3 rename; abort the whole apply with a clear 'file changed since preview' error if any mismatch. Pair with a model/root-level apply lock (see the deterministic-path finding) so the check-then-write is atomic against sibling sessions.
- **Verification:** Test: two handlers sharing one pooled model; A previews transform of X, B previews+applies a different transform of X, then A applies. Assert A's apply either errors out or preserves B's change (X still contains B's edit). Before fix: B's change is gone; after fix: apply rejects or merges safely.

### F5 — [HIGH] ApplyWithBackup step-3 rename loop is not atomic and has no rollback on partial failure

- **Location:** `go/forest/forest.go:228`
- **Dimension:** -
- **Invariant violated:** A multi-file apply must be all-or-nothing: either every FileChange lands on disk or none does.
- **Failure scenario:** A transform produces changes to files A, B, C. Step 3 renames temps into place one at a time. If the rename for B fails (e.g. B's parent dir is read-only, B is a directory, a permission/immutability error, or an EXDEV cross-device error), A has already been overwritten with new content, B and C still hold their originals, and ApplyWithBackup returns an error with A modified and C not. The codebase is left in a syntactically inconsistent half-applied state (e.g. a renamed symbol updated in A's call sites but not C's), and there is no rollback of the already-renamed A. Already-written staging temps for C are also orphaned (CleanupBackups is never called on this path).
- **Evidence:**

```
// Step 3: Rename staging files to final paths.
	for i, change := range changes {
		if parent := filepath.Dir(change.Path); parent != "" {
			if err := os.MkdirAll(parent, 0o755); err != nil {
				return nil, fmt.Errorf("creating directory %s: %w", parent, err)
			}
		}
		if err := os.Rename(tempPaths[i], change.Path); err != nil {
			return nil, fmt.Errorf("renaming temp to %s: %w", change.Path, err)
		}
	}
```

- **Fix sketch:** Make step 3 recoverable: track successfully-renamed targets, and on any rename error restore each already-renamed file from its backup (or from the pre-move temp) before returning. Alternatively write all temps, fsync, then attempt renames and on first failure reverse the completed renames using the backups. Always clean up leftover temps on failure.
- **Verification:** Before: unit test with three changes where the second target path is made un-renamable (e.g. chmod 0500 its parent dir); assert that after the failed ApplyWithBackup, file A still equals its original — it currently equals NewSource (partial apply). After the fix, A is unchanged and the error is returned.

### F6 — [HIGH] Pattern DSL captures ignore bracket nesting, mis-splitting arguments and emitting corrupt code (migrate_pattern / apply_equivalence)

- **Location:** `go/mcp/pattern.go:105`
- **Dimension:** -
- **Invariant violated:** A $placeholder capture must respect balanced brackets/parens: a capture spanning an argument must not straddle a nested delimiter. matchFrom instead does shortest-substring matching against raw node text with zero nesting awareness.
- **Failure scenario:** migrate_pattern old_pattern="foo($a, $b)" new_pattern="foo($b, $a)" (a common expected/actual swap, e.g. assertEquals) applied to source containing `foo(bar(1, 2), 3)`. Match splits on the FIRST ", " so it binds a="bar(1", b="2), 3" instead of a="bar(1, 2)", b="3". Apply then produces `foo(2), 3, bar(1)` — syntactically invalid, semantically nonsense — which is stashed as a pending change and written verbatim on apply. Verified by direct execution of the matcher: `match=true caps=map["a":"bar(1" "b":"2), 3"]` -> rewrite `foo(2), 3, bar(1)`.
- **Evidence:**

```
// Try shortest match: from srcPos to the first occurrence of nextLiteral.
	for end := srcPos; end <= len(source); end++ {
		if nextLiteral != "" && !hasAtPos(source, end, nextLiteral) {
			continue
		}
		// Try this capture length.
		captures[seg.Placeholder] = source[srcPos:end]
		if p.matchFrom(source, end, segIdx+1, captures) {
			return true
		}
	}
```

- **Fix sketch:** Make the placeholder capture bracket-aware: when scanning for the next literal boundary in the shortest-match loop, only accept an `end` position where paren/bracket/brace depth (tracking '(' ')' '[' ']' '{' '}', ideally skipping string/char literals) is balanced relative to srcPos. Equivalently, reject candidate splits that occur inside an unbalanced group. Alternatively match against the CST (child argument nodes) rather than raw text.
- **Verification:** Before: add a Go test calling ParsePattern("foo($a, $b)").Match("foo(bar(1, 2), 3)") and assert caps["a"]=="bar(1, 2)" && caps["b"]=="3" — it fails (a="bar(1"). Or run migrate_pattern on a file with a nested call and inspect the diff. After the fix the same assertions pass and the migrate_pattern/apply_equivalence diff is well-formed.

- **Location:** `go/mcp/tools.go:1239`

### F8 — [HIGH] Concurrent map read/write on SummaryVecs crashes the whole daemon (fatal, uncatchable)

- **Location:** `go/model/retrieve.go:196`
- **Dimension:** -
- **Invariant violated:** A Go map that is mutated in place must never be read/ranged by another goroutine without holding the guarding lock for the entire read. SummaryVecs is written in place under vecsMu.Lock (summary.go:137) but ranged without the lock.
- **Failure scenario:** Daemon started with SAWMILL_EMBED_MODEL set and SAWMILL_SUMMARISE=1. cosineSearchOnIndex takes vecsMu.RLock, copies the SummaryVecs map *header* into local `vecs` (line 176), then RELEASES the lock at line 180 and ranges over the same underlying map at line 196 (`for id, v := range vecs`). Concurrently the background summariser goroutine lands a new summary embedding: `s.m.SummaryVecs[item.SymbolID] = vecs[0]` (summary.go:137) under vecsMu.Lock. Because the reader is no longer holding any lock during the range, the Go runtime detects a concurrent map read + map write and throws `fatal error: concurrent map read and map write`, aborting the entire process and killing every MCP session. The window is wide: the range walks the full (potentially thousands-of-entries) map and the summariser writes continuously. Note Vecs is safe because it is only ever replaced wholesale (m.Vecs = loaded, model.go:576); only SummaryVecs is mutated in place.
- **Evidence:**

```

... vecs = m.SummaryVecs ...
m.vecsMu.RUnlock()   // line 180 — lock released here
...
for id, v := range vecs {   // line 196 — unlocked range
    scored = append(scored, idScore{id: id, score: embed.Cosine(queryVec, v)})
}
// summary.go:137 (concurrent, under Lock): s.m.SummaryVecs[item.SymbolID] = vecs[0]
```

- **Fix sketch:** Either hold vecsMu.RLock across the entire ranging loop (move the RUnlock past line 198), or snapshot the map contents into a local copy under the RLock before ranging, or make the summariser replace SummaryVecs wholesale (copy-on-write) exactly like Vecs. Prefer snapshot-under-lock or COW so the slow cosine loop does not hold the lock and block the summariser.
- **Verification:** Add a test using an in-memory embedder with the summariser enabled that calls SemanticSearch in a tight loop while another goroutine writes new SummaryVecs entries; run under `go test -race`. Before fix: `fatal error: concurrent map read and map write` (or race report). After fix: clean. No existing test enables the summariser, so CI's -race never exercises this path today.

### F9 — [HIGH] Deterministic backup/staging paths + no cross-session apply lock corrupt backups and break undo on concurrent same-file applies

- **Location:** `go/paths/paths.go:58`
- **Dimension:** -
- **Invariant violated:** Backup and staging paths must be unique per in-flight apply so concurrent (or repeated) applies cannot overwrite each other's originals; undo must always be able to recover the pre-apply state.
- **Failure scenario:** BackupPath/TempPath are pure functions of (root, relative path) — BackupDir(root)+rel+'.bak' / '.new'. handleApply only takes the session-local h.mu (server.go:64); there is no model- or root-level lock, so two sessions sharing model R applying a change to the same file X run ApplyWithBackup concurrently. Both write the identical TempPath(R,X) (last writer wins, e.g. B's content), both copyFile X into the identical BackupPath(R,X), both rename temp->X, so X ends up with B's content while A reports success (A's change lost). Both A.lastBackups and B.lastBackups point at the same .bak. A.undo restores the original and removes the .bak (forest.go:277); B.undo then hits os.Stat(backup) IsNotExist and `continue`s (forest.go:251), silently restoring nothing. The pre-apply states are unrecoverable. The same deterministic-path root cause also makes a single session's second apply overwrite the first apply's backup, so the original can only be recovered for the most recent apply.
- **Evidence:**

```
func BackupPath(root, originalPath string) string {
    rel, err := filepath.Rel(root, originalPath) ...
    return filepath.Join(BackupDir(root), rel+".bak")   // deterministic; two applies of same file collide
}
func TempPath(root, originalPath string) string { ... return filepath.Join(BackupDir(root), rel+".new") }
```

- **Fix sketch:** Serialize applies per model/root with a model-level mutex (closes the concurrent window and makes ApplyWithBackup atomic against siblings), AND make TempPath/BackupPath unique per apply (include a random apply-id path component) with an undo manifest mapping backup->original. The mutex alone fixes the concurrent case; unique paths additionally fix repeated single-session applies.
- **Verification:** Test with two handlers sharing one pooled model applying to the same file concurrently, then undo both. Assert both applied changes are either preserved or cleanly rejected, and that undo restores the correct content. Before fix: one change is lost and one undo no-ops; after fix: consistent.

### F10 — [HIGH] rename is scope-blind: renames every identifier whose text matches, across all bindings and the whole codebase

- **Location:** `go/rewrite/rewrite.go:79`
- **Dimension:** -
- **Invariant violated:** A rename must only rewrite the specific binding the user named. ```


- **Fix sketch:** Resolve the binding before rewriting: use the available LSP pool (gopls etc.) for a true rename, or at minimum restrict identifier nodes to those resolving to the same declaration (definition site) as the user's target. - **Verification:** Before: on a two-struct fixture, run rename from="X" to="Width" and observe both structs mutated; on the builtin fixture, `go build` the applied result and observe the `cap(3,4)` compile error. After: rename touches only the targeted binding and `go build` succeeds.

### F18 — [MEDIUM] Concurrent SQLite writers with no busy_timeout / unbounded pool cause SQLITE_BUSY; manager silently drops index updates (stale index)

- **Location:** `go/store/store.go:95`
- **Dimension:** -
- **Invariant violated:** Index writes from the manager goroutine, the summariser, and handler teach_* calls run concurrently on one shared *sql.DB; they must not silently fail, and the persisted index must stay coherent with disk after edits.
- **Failure scenario:** Open() uses DSN = bare path with no busy_timeout and never calls SetMaxOpenConns, so database/sql opens multiple connections and WAL permits only one writer at a time. When the manager reparses a changed file (UpsertFile/UpdateSymbols/UpdateRefs/RecomputeImportance, all writes) while a session calls teach_convention or the summariser writes UpsertSummary, the second writer gets `database is locked (SQLITE_BUSY)` immediately. Empirically reproduced against modernc.org/sqlite in this module: 1527 of 1600 concurrent inserts failed with SQLITE_BUSY. The manager swallows the error (model.go:566-569 use `_ =`), so that file's symbols/refs are not updated — find_symbol/search_code/graph_expand then return stale or missing entries and a subsequent rename/transform targets the wrong or an empty set. The handler teach_* call surfaces a spurious 'database is locked' error to the user.
- **Evidence:**

```
db, err := sql.Open("sqlite", path)   // no ?_pragma=busy_timeout, no SetMaxOpenConns
...
_, err := s.db.Exec(`PRAGMA journal_mode=WAL; ...`)   // WAL: single writer, no busy handler
// model.go manager swallows write errors:
_ = m.Store.UpsertFile(...); _ = m.Store.UpdateSymbols(...); _ = m.Store.UpdateRefs(...)
```

- **Fix sketch:** Open with a busy timeout (modernc DSN `file:...?_pragma=busy_timeout(5000)` or `PRAGMA busy_timeout=5000` in init) and serialize writes (db.SetMaxOpenConns(1) or a dedicated single-writer goroutine) so writers queue instead of failing. Stop swallowing write errors in the manager — at minimum log, ideally retry on BUSY.
- **Verification:** Reproduced with a standalone concurrent-writer test (8 goroutines x 200 inserts) against modernc.org/sqlite: >1500 `database is locked (SQLITE_BUSY)` errors with the current settings. Re-run after adding busy_timeout + SetMaxOpenConns(1): expect zero errors. Add a regression test that runs manager-style writes concurrently with teach_* and asserts no BUSY errors and that all writes land.
